# 房间分类是跨平台的一元一等实体、归房间库所有，房间顺序按分类各自独立

用户添加的房间多起来后需要「分类 + 分类显示」。本项目此前**没有任何分类 / 分组 / 标签概念**——`streamers[].category` 是平台给的内容分类（斗鱼 `cate_name`），是观测量、不是组织维度，不可复用。分类的建模有六件事同时被钉死，它们互相牵制，所以合记在这一条 ADR 里。

**一、互斥，不是标签。** 一个房间至多归入一个分类（`rooms[].categoryId` 是单个值，不是数组）。理由是「分类」这个词在中文里就是互斥心智，且只有互斥才能让弹窗切成互不重叠的段落。代价是「游戏 + 主播」这类叠加表达不了——真要叠加，那是多标签，是另一个功能、另一条 ADR，存储形状要改。

**二、跨平台统一，是「平台为第一维」的唯一例外。** `CONTEXT.md` 开篇写着「房间、主播、通知、设置开关均以平台为第一维划分」，分类刻意不遵守：一个「游戏」分类同时装斗鱼与 B 站房间。因为用户的组织诉求是「按内容看，不按平台看」，而平台维在卡片上已有 `platform-tag` 承担。这是本仓库第一处成文的例外，`CONTEXT.md` 的「分类」条目已标明。

**三、一等实体，归房间库所有。** 分类是单独一份列表（`categories: [{ id, name }]`，数组顺序即分类顺序），房间只记 `categoryId`；不是「把分类名写在房间上」。因为改名要一次生效、分类要能在没有房间时继续存在、分类顺序要有明确来源——这三件事在字符串字段上都做不到（改名要批量扫同名房间、空分类无法存在、顺序只能靠「首次出现」或名称排序推断）。落点是房间库（`lib/room-store.js`）新增的第四个键，而不是一个仿 `lib/room-identity.js` 的新 module：分类成员关系本身就是房间形状的一部分（`rooms[].categoryId`），而「删除分类 → 清空其下房间的 `categoryId`」是对 `rooms` 的一次写入，分类若归别的 module，这次写入就绕过了 ADR-0003 的单写者边界。

**四、房间顺序按分类各自独立。** 旧模型是全体房间一份顺序（`reorderRooms`，同时重排 `rooms` 与 `streamers`）。分类出现后，每个分类内部各自保留一份相对顺序、互不影响；分类之间的先后由分类列表顺序决定，用户拖拽分类标题调整。`reorderRooms` 因此改成分类内重排：只置换目标分类成员所占的槽位，其余分类的相对顺序不动，`streamers` 仍同步重排。落点规则统一成「追加到目标分组末尾」——换分类、删分类回落未分类、新建房间都遵守同一条，不引入额外的历史状态。

**五、「未分类」是虚拟桶，不是分类。** 房间的 `categoryId` 为空就是未分类：它不落盘、不在分类列表里、不能改名 / 删除 / 拖拽 / 排到后面，在弹窗与设置页都固定排在最前。「未分类」同时是保留名，不允许建成真分类（否则分组标题会重复出现、语义分叉）。

**六、纯组织，不承载行为。** 分类不影响任何通知：不做「整个分类静音」，不做「新房间继承分类的通知开关默认值」。`notify` / `watch` / `viewerAlert` / `surgeAlert` / `highlightAlert` 五个 per-room 开关与它们的全局总开关，判定链一行都不改。分类只决定分组与顺序。

**显示规则**（与前六条一起定下）：弹窗的在线列表按分类分段，**只渲染有在播房间的分类**，标题是「分类名 + 在播数」；设置页是完整列表，渲染**所有**分类（含空的、含全部未开播的），标题是「分类名 + 在播数/总数」。两端只要该界面有房间就**始终显示分类标题**——哪怕只有一个非空分组、哪怕全部房间都还在未分类；两端都**不折叠**。归类走房间卡片上的分类下拉（含「新建分类…」）；拖拽只负责分类内排序，拖到别的分类区段上回弹（同一个手势不做两件事，归类只有下拉一个入口）；添加房间的表单同样带分类下拉、默认「未分类」。分类标题就地改名 / 删除，删除时二次确认并报出受影响的房间数（房间本体不删，回落未分类）。设置页的房间卡片与弹窗的统计、盯守排队提示等既有元素一律不动，只是被装进分组里。

## Considered Options

- **分类名直接写在房间上**（`rooms[].category` 字符串）：机械改动最小；但改名要批量改同名房间、空分类无法存在、分类顺序只能靠推断（中文名称的字典序通常不是用户要的）。故取一等实体。
- **分类归一个新 module**：词表上更干净；但「删除分类要清空其下房间的 `categoryId`」会变成对 `rooms` 的第二次写入，只能靠两次写 + 补偿（非原子）或消息回环，为一份只有一个字段的列表付不起。
- **多标签（`categoryIds` 数组）**：能表达「游戏 + 主播」这类叠加维度；但显示要按标签分桶（同一个房间出现在多段）或改用筛选 chips，管理界面也要多选控件。用户要的是互斥的「分类」，故否决。
- **两级分类（分类下分子类）**：表达力更强；但弹窗空间小、设置页要做树形、`categoryId` 要变成路径或父指针。当前房间量级不需要层级。
- **「未分类」做成分类列表里预留 id 的一条真分类**：结构上只剩一种东西；但它必须处处特判（不可改名 / 删除、必须钉在第一位、不能被拖到中间），用户还能再建一个同名的「未分类」，等于把一个假分类的规则泄漏给每一处消费方。
- **保留全局一份房间顺序**（分类只做渲染时的分组，不新增顺序状态）：零排序改动、`reorderRooms` 一行不动；但用户要的是「把某个分类里的房间单独排一下」，全局顺序做不到——在分类内拖动会连带改变该房间在别的分类视角下的位置。取舍是排序模型的复杂度换控制力，取后者。
- **跨分类拖拽顺带改分类**：手感连贯、不用去点下拉；但同一件事两个入口，且「拖到哪一行」同时表达了分类与顺序，拖到标题行 / 空分类上的行为都要额外定义。
- **弹窗加分类筛选 chips / 可折叠分段 / 空分类也显示**：房间多时省滚动；但弹窗就是「一眼看在播」的小窗（近期刚为小尺寸重排过今日统计布局），加筛选和折叠会把只读展面变成需要操作的面，空分类标题还会把列表撑长。
- **分类必填**：列表永远干净；但存量房间必须先建好分类才能升级，每次加房间也多一步。故保留「未分类」桶。
- **删分类直接删 / 非空不允许删**：直接删在房间多时看不出影响面；非空禁止删最安全但最麻烦。二次确认 + 报房间数取中间。

## Consequences

- **迁移零成本**：老安装没有 `categories` 键（读侧回退空数组，`init()` 的 seed 判定要认得这个新键），所有房间 `categoryId` 为空 → 全部落在「未分类」，而该段内的相对顺序直接沿用现有 `rooms` 数组顺序。升级后的视图与升级前逐行一致。
- 房间库新增第四个键与一组意图式操作（建 / 改名 / 删 / 重排分类、设置某房间的分类），编排新增对应消息类型（`ADD_CATEGORY` / `RENAME_CATEGORY` / `REMOVE_CATEGORY` / `REORDER_CATEGORIES` / `SET_ROOM_CATEGORY`），弹窗与设置页改吃 `snapshot()` 里的 `categories`。
- 分组与顺序是**一条规则、两处消费**（弹窗与设置页），所以它照 ADR-0005 的惯例收进一个纯模块（名称校验、重名与保留名判定、「未分类固定最前」的分组、隐藏空分类与否），页面只渲染它的结论，不各自再实现一遍。
- 名称约束：trim 后非空、有长度上限、唯一、不得等于「未分类」。分类 id 由房间库生成、不暴露给用户——保留「空值」专门表示未分类。
- `reorderRooms` 的调用方（设置页拖拽）要跟着改：拖拽范围限制在分类段内，提交的重排请求要带上所在分类。`test/room-store.test.cjs` 钉存储形状的用例需要扩写（分类增删改与重排、重名与保留名拒绝、删分类后回落未分类并追加末尾、分类内重排不动其他分类、缺 `categories` 键的老数据）。
- 分类**不**触碰通知、统计、采样、盯守任何一条链路，也不参与观众数提醒 / 弹幕激增 / 看点通知的判定。任何把分类接进判定链的改动，都要先回答「分类是组织维度，凭什么影响行为」——这是本决策最容易被当成「顺手加个静音」而绕开的地方。
- 弹窗仍是只读展示面：不在弹窗里归类、改名、删除。
