# 「今日统计」轮询第三方数据站 doseeing，按斗鱼房间每 5 分钟取当日累计、只读展示不通知

弹窗的在线列表要显示每个在线房间**当天 0 点起累计**的四个数字：弹幕数 / 弹幕人数、礼物金额 / 礼物人数（见 CONTEXT.md「今日统计」）。斗鱼官方的公开接口只给房间快照与当前指标，不给区间聚合成品；能直接给出这四个数的是第三方数据站 `doseeing.com`（在看直播排行榜）的 `GET /api/room_stat?room=<rid>&hours=today`——实测匿名可访问，无签名、无 token，`hours` 是白名单枚举（`1` / `today` / `yesterday` / `7day` / `thismonth`）。因此本项目**第一次引入非斗鱼 / 非 B站的第三方接口依赖**，这是这条 ADR 要记录的核心取舍。

取数落在新增的 vendor 模块 `lib/doseeing-api.js`（`fetchTodayStats(roomId)`，自带超时与错误模型，字段收敛在此：`room` 为 `null` 视为 `room_not_found` 失败，`gift.paid.price` 单位是**分**、在此换成元并保留两位小数），装配根新增一个独立的 `todayStatsApi` port 注入编排——不与 `lib/douyu-api.js` 合并，因为仓库的惯例是一个模块对一个接口提供方，混进去会让「这个数从哪来」在代码里消失。判定归新增的纯规则模块 `lib/today-stats.js`（照 `lib/highlight-alert.js` 的形状）：平台门 `STATS_PLATFORMS = ['douyu']`、总开关 `isTodayStatsEnabled`、取数目标 `selectTodayStatsTargets`、保鲜判定 `isStatsFresh`。取数是一条独立的 5 分钟 `chrome.alarms` 任务，承载它的 alarm 只在「总开关开启 且 至少一个斗鱼房间」时存在，照 `syncHighlightAlert` 的收敛法；结果写进编排自己持有的 `todayStats` 键（`{ [房间复合键]: { chatPv, chatUv, giftAmount, giftUv, date, fetchedAt } }`），弹窗只读，照它读 `watchQueued` 那样。全局总开关 `settings.todayStatsEnabled` 默认开启；关掉后不请求、不展示，已落盘的数字保留（与「关闭总开关后各房配置保留、重开即恢复」的既有口径一致）。

**只对斗鱼房间取数**，不只是因为 doseeing 只有斗鱼数据，还因为拿 B 站房间号去查会**错标**：两个平台的房间号是各自独立的命名空间，不存在的号返回 `room: null`（统计全 0），而恰好与某个真实斗鱼房间同号的 B 站房间会返回**那个斗鱼房间**的统计——把它显示在你的 B 站卡片上就是纯污染。平台门因此是正确性问题，不是省请求的优化。取数目标是「开播中 且 斗鱼」的房间：下播房间的卡片本就不显示，查了也没有出口。

**「礼物金额 / 礼物人数」取付费礼物**（`gift.paid.*`），不含免费礼物：含免费的口径会把「礼物人数」抬到接近观众数、失去区分度（实测同一房间同日 付费 198 人 vs 含免费 349 人），站点自己也把付费礼物单独称为 SR值 / 收入。

生命周期四则：单房取数失败**不动该房旧值**、只记日志（一次接口抖动不该让数字忽隐忽现）；跨过本地零点后 `date` 不是今天的旧值**判废不显示**（`isStatsFresh`），避免把昨天的「today」当今天；房间被移除时清掉该房条目（照 `clearHighlightWatermark`）；总开关关闭时 alarm 清除、弹窗隐藏该行。

## Considered Options

- **复用 60 秒的开播状态轮询**（在 `refreshRooms` 合并完接着取）：少一个 alarm 与一套创建 / 清除收敛；代价是对第三方站点的请求量翻 60 倍，且取数节奏被用户的「轮询间隔」设置间接绑架。
- **复用 10 分钟观众数采样 alarm**：不新增 alarm；但那个 alarm 的存在由「贵宾数采集开关」决定，会出现「关掉贵宾数采集，今日统计也没了」这种莫名其妙的联动（ADR-0006 已为看点否决过同一做法）。
- **弹窗打开时现取，不落盘**：永远最新、零后台开销、不新增 alarm 与存储键；但弹窗里会出现本项目第一处页面网络请求，弹窗关得快可能把请求掐断，且推翻「弹窗只读存储、取数都在 SW」的既有形状。
- **落进房间库的 `streamers` 字段**（照 `vipCount` / `rankCount`）：弹窗读快照即可、修剪随房间删除天然发生；但这是第三方当日累计观测，不是「某个房间当前的开播信息快照」，收进去要扩写 ADR-0003 的单写者边界，换不来真实收益（ADR-0006 曾为同类状态否决同一落点）。
- **不加总开关，始终请求**：最省事；但新增了第三方依赖却无法退出，且与「每个功能都有总开关」的既有口径不一致。逐房开关则相反——对一个只读展示项属于过度配置。
- **顺带显示同一响应里的 `ol`（在线人气）**：白拿一个数据点；但卡片上已有「贵宾数 / 高能榜」这一档观众指标，再放一个口径不同的「在线人气」会让同一个问题出现两个互相矛盾的数字（实测同房 28.4 万 vs 贵宾数），用户无法分辨。
- **展示上把四项按房间聚合到页面顶部**：信息密度高；但「弹幕人数」「礼物人数」是去重口径，跨房相加会把同一人重复计数，合计出来的「人数」在语义上是错的。逐房展示才成立。
- **把探针脚本 `.scratch/doseeing-api/fetch-room.js` 挪进正式目录**：可复用的手测工具；但它是一次性逆向探针，错误处理与仓库的 API 层不一致、容易分叉。接口契约改由新 API 模块的单测夹具（录制的 JSON 响应）钉住，探针留在 `.scratch`（已 gitignore）。

## Consequences

- `manifest.json` 的 `host_permissions` 必须新增 `https://www.doseeing.com/*`，否则 SW 与扩展页都无法直接 fetch。用户更新扩展时会看到新域名授权——这是引入第三方依赖唯一可见的代价，也是它难以回退的原因。
- README 的功能表、支持平台表（今日统计只有斗鱼）与**隐私章节**都要改：现在写的是「所有请求都由浏览器直接发往斗鱼 / B 站的公开接口」，而本功能会把「你在监控哪些房间」以匿名 GET 的形式发给 doseeing.com。设置页「刷新与采样」卡片新增 `todayStatsEnabled` 开关及其来源说明。
- `lib/today-stats.js` 要进 `background.js` 的 `importScripts`（排在使用它的模块之前）、`test/service-worker-entry.test.cjs` 的 `LIB_FILES`（同序）、以及 `popup/popup.html` 的 `<script>`（弹窗要用 `isStatsFresh` 判废）；`ROOM_STORE_SETTINGS_KEYS` 与 `ROOM_STORE_DEFAULTS.settings` 各增一项。
- 数据可用性完全不由本项目掌控：doseeing 挂了、改接口或加限流策略，对应的就是数字不显示（旧值在跨零点后判废），不影响开播通知、弹幕检测、观众数提醒、弹幕激增、看点通知五条链路中的任何一条。这是把它做成纯附加展示、不做降级备份的原因——它是唯一来源，没有替代。
- 弹幕数的口径与弹幕激增的「条数」必然对不上（一个来自第三方整房统计，一个是本地检测长连接的观测值）。这不是 bug，是两套来源；`CONTEXT.md` 的「今日统计」条目已写明不许把它们互相当作校验。
- 四项数字的展示是只读的，不参与排序、不触发通知、不影响房间顺序与角标；未来若要用它做提醒，那是另一个功能，需要先解决「第三方数据的延迟与可信度」这两件事。
