# 斗鱼房间号支持靓号：betard 直查失败时拉房间页解析内部 room_id

斗鱼的房间号有两种形态：**内部 `room_id`**（接口认的那个）与**靓号**（用户在 `https://www.douyu.com/<号>` 地址栏里看到的短号，房间页内嵌数据里叫 `vipId`）。扩展此前的 `DouyuAPI.fetchRoomInfo` 直接把用户输入的号拼进 `https://www.douyu.com/betard/<号>`，而 betard 只认内部 `room_id`：拿靓号去查，斗鱼不返回 JSON 而返回一页「提示信息 / 该房间目前没有开放」的 HTML，`JSON.parse` 失败，被收敛成取数失败。

实测（2026-10-04）：`betard/91224` → HTML；`betard/8727436` → JSON；房间页 `https://www.douyu.com/91224` 内嵌 `{"roomInfo":{"room":{"room_id":8727436,"vipId":91224,...}}`；反过来 `https://www.douyu.com/8727436` 307 跳到 `/91224`。也就是说 `91224` 是「暖妹QWQ」的靓号，内部号是 `8727436`，而 betard 只按内部号给数据。这个失败叠加 ADR-0014 记录过的跨平台兜底，就酿成了工单里的「添加斗鱼 91224 却跳到 B 站」。

本决策：**在斗鱼平台内部把靓号解析成内部 `room_id`**。`fetchRoomInfo` 先用输入号直查 betard；失败且该输入号没有缓存映射时，拉一次房间页，用纯函数 `extractInternalRoomId` 从内嵌数据里取出内部号，再用内部号直查一次；成功则把「输入号 → 内部号」写进 SW 实例内的缓存。要点三条：

- **解析要能自证对应关系**。页里只认带 `roomInfo.room.room_id` 的内嵌块，且要求块内的 `room_id` 或 `vipId` 等于输入号——无效号页里可能内嵌推荐房间的数据，不做这道守卫就会错取成别人的房。
- **对外 `data.roomId` 回显调用方传入的号**（靓号或内部号），不是解析出的内部号。存储与轮询合并都以调用方传入的号为复合键（`platform_roomId`），回显内部号会让快照挂不到房间上（`_mergeStreamers` 按 `room.roomId` 取键）。
- **只缓存成功**。网络 / 风控导致的偶发失败不写缓存，下一轮重试即可；否则一个抖动会把靓号永久判死。

看点取数（`fetchHighlights` 的 `rid`）同样只认内部号：**已按 ADR-0017 改由调用方传入内部号**（编排取房间条目的 `internalRoomId`），`fetchHighlights` 不再自行查这份缓存，冷启动的 SW 也能取到。

## Considered Options

- **在斗鱼 API 内部透明解析、存储保留用户输入的靓号（选用）**：`roomId` 仍是用户在设置页输入、也是直播地址里看到的那个号（`douyu.com/91224` 照常可点），与 CONTEXT.md 对「房间号」的定义一致；改动只落在 `lib/douyu-api.js` 一个 module。
- **把解析出的内部号存成 `roomId`**：下游（轮询、看点、弹幕 joingroup）都用内部号，最干净，且 `douyu.com/8727436` 会自动 307 到靓号页、URL 仍可用；但它**在用户背后替换了输入号**，设置页会显示 `8727436` 而不是用户输的 `91224`，与「房间号是用户输入」的领域定义冲突，且需要改 `resolveNickname` 的返回契约与房间库的写入路径。属于与 ADR-0014 同类的「静默替换」，不做。
- **找一个直接认靓号的轻量接口**：实测均不可用——`m.douyu.com/api/room/info` 对已知房间也回「参数错误」；`www.douyu.com/lapi/live/getH5Info`、`japi/weblist/apinc/roomInfo` 404；`open.douyucdn.cn/api/RoomApi/room/<号>` 早已停更（对靓号回 `Not Found`）。房间页内嵌数据是目前唯一可靠的映射来源。
- **给斗鱼请求补 `Referer` / `Cookie` 让 betard 认靓号**：最初的假设，实测证伪——betard 对内部号（含 `9999`）不带任何请求头就正常返回 JSON，`Referer` 与结果无稳定相关；失败的唯一变量是「传的是靓号还是内部号」。补头解决不了这个问题（早期观察到的相关性是我提取判据写错造成的假象）。

## Consequences

- 靓号房间每轮少走一次直查、多一次「页面解析 → 用内部号直查」；缓存命中后稳态只发 `betard/<内部号>` 一次请求，页面只在一个 SW 实例内首次解析时拉一次。普通房间（内部号）不受影响，路径与以前完全一致。
- 弹幕 WebSocket 的 `joingroup rid@=` 当时仍用存储里的号（靓号），因为采样回调按同一个号回报贵宾数、必须与存储键一致。实测（2026-10-04）确认斗鱼弹幕服务端不认靓号——靓号房间的贵宾数采样、弹幕检测、弹幕激增全部收不到数据（开播状态、通知、跳转 URL 不受影响）——**这一项已被 ADR-0017 解决**：线上改用持久化的内部号，回调仍回映存储里的号。
- 解析完全依赖「房间页内嵌 `roomInfo.room.room_id`」这一页面结构；斗鱼改版会使靓号解析失效（普通房间不受影响）。守卫（内部号或 `vipId` 必须等于输入号）保证失效时只表现为「解析不到」而不是「解析成别的房」。
- 与 ADR-0014 配套：平台不再跨平台兜底，斗鱼靓号在平台内部被正确解析，两条合起来消除「添加斗鱼房间却跳去 B 站」这一缺陷。
