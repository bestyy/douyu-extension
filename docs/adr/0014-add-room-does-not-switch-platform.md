# 添加房间以所选平台为准，解析失败不改挂到另一个平台

设置页添加房间时平台是用户在下拉里显式选的，但 `RoomStore.addRoom` 在所选平台解析昵称失败之后，会拿**同一个数字**去另一个平台再试一次，成功就把房间静默记成那个平台。这段逻辑写在代码注释里（「所选平台解析失败自动换另一平台兜底」）并有单测钉住（`test/room-store.test.cjs` 的「自动换另一平台兜底，兜底后同样查重」），本意是让用户少一步、只输号码也能加上。

它的前提是错的：**数字房间号只在平台内唯一，跨平台会撞号**。2026-10-04 的真实工单兑现了这个缺陷——用户添加斗鱼直播间 `https://www.douyu.com/91224`，斗鱼侧解析失败（该号是靓号，`betard` 只认内部 `room_id`，见 ADR-0015；当时的代码把这次失败当成了「号码有误」），兜底逻辑转向 B 站，而 `91224` 在 B 站是另一间房（主播「大画家的笔」）。房间于是被存成 `bilibili_91224`：弹窗卡片显示「B站」标签和 B 站昵称，点击跳去 `https://live.bilibili.com/91224`，用户真正想看的斗鱼主播（「暖妹QWQ」）从未被监控。添加成功的提示只回昵称、不回平台，用户很难当场察觉。

因此本决策：**平台是用户显式选择的身份，解析失败只在所选平台上报错，绝不改判到另一个平台**。`addRoom` 只在所选平台解析一次，失败即返回「房间号不存在或无法访问」，不写盘；预检与临界区内查重也随之收敛到所选平台一个维度。这条与「未知平台显式拒绝、不静默当成斗鱼」是同一立场的两个面：平台这件事上，**任何静默替换都不做**。

## Considered Options

- **去掉跨平台兜底（选用）**：改动最小，消除整类「加错平台」的缺陷；代价是丢掉了「只输号码自动认平台」的便利——但那个便利本就是这段兜底带来的，且设置页的平台下拉一直是必填的（缺平台直接拒绝），从来没有真正「不用选平台」的路径。
- **保留兜底，但改为弹确认**：跨平台替换仍可能，只是让用户点头；实现上要在设置页与 `addRoom` 之间加一轮确认交互，而绝大多数情况下用户只是想要一个明确的成功 / 失败，多一步交互换来的是把一个本该拒绝的情况变得模棱两可。
- **先做一次「房间号在所选平台不存在」的确定判定，再决定要不要换平台**：听上去更聪明，但号码撞号时并不存在「正确」的平台——`91224` 在斗鱼是一间房、在 B 站是另一间房，两边都不是错的；这时换平台与否都是用一个推断覆盖用户的显式选择。自动换平台只在「用户其实没选平台」时才有意义，而那种情况在 UI 上不存在。
- **保留兜底但在成功提示里回显平台**：至少用户能看见平台被换了；但这只是给一个不该发生的替换补一个告警，缺陷本身还在（房间已经加错、点进去已经跳走）。

## Consequences

- 斗鱼靓号这类「所选平台解析失败但房间其实存在」的情况，改由 ADR-0015 在平台内部修好，不再依赖跨平台兜底——两条决策配套：先让所选平台的解析尽量不难失败，再保证失败时不越界。
- 所选平台解析偶发失败（网络抖动 / 平台风控）时，用户会看到一次错误、需要重试，而不是被悄悄加到另一个平台。宁可要一个明确的失败。
- `RoomStore` 的 `resolveNickname` port 语义收窄为「只解析所选平台」；装配根 `background.js` 的 adapter 不变（它本来就只转发单个平台）。
- 读取旧数据不受影响：`rooms` 里历史上被兜底记错平台的房间不会自动纠正——平台无法从数据本身推断，只能由用户移除后按正确平台重新添加。
