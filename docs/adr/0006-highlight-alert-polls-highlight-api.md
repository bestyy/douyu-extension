# 看点通知轮询斗鱼的看点接口，按每房看点水位去重、只报最新一条

「看点」是斗鱼独有的形态：平台自己把直播片段切成带标题的精彩时刻，房间未开播时拿不到（实测大主播下播后 `playback` 与 `highlightList` 双双为空），直播中也可能长期一条都没有。因此看点通知**只对斗鱼存在**，也**不能拿房间快照里的任何字段做代理**——判定只看看点列表本身（`sort:0`，最新在前）。

取数是一条独立于开播状态轮询的周期任务：每 5 分钟一轮，只请求「开了该房看点开关 **且** 当前开播」的斗鱼房间（`POST /wgapi/vodnc/center/ailive/getHighlightDetail`，匿名可用、不需要登录，`host_permissions` 已覆盖 `www.douyu.com`）。周期写死 5 分钟、不做设置项：看点由平台事后分析生成，通知本来就晚于直播画面几分钟，把轮询压到 1 分钟换不来体感，请求量却是 5 倍。承载它的 alarm 只在「至少一个斗鱼房间开了看点」时存在、全关掉即清除，照 `danmakuSurgeTick` 的收敛法，不给 SW 留无用唤醒。

「新的看点」按**每房看点水位**判定：水位 = 该房已经通知过的最大看点编号（平台给的编号全局递增，实测跨房相邻）。**首次观测只记水位、不发通知**（刚打开开关、刚加入房间、水位丢失都走这条，与 `_firstRun` / `addRoom` 对开播通知的处理同构）；此后编号大于水位的算新。**一次发现多条只报最新那一条**、正文提示另有几条：通知 ID 是「房间复合键 + `_highlight`」、同房反复触发只覆盖不堆积，逐条发等于多响几声多闪几次，用户看到的还是最后那一条。水位记的是「已经通知过」，不是「用户看过」——通知躺在通知中心没点开也算通知过了。请求失败或返回空列表时**不写水位**（原地不动），下次成功时仍会通知最新那一条，不让一次接口抖动吃掉一条看点。

不加热度门槛、也不加冷却：实测节奏 10–25 分钟一条，平台自己的发布节奏就是节流阀；而热度跨房间完全不可比（实测同场 1.1 万–6.8 万、另一场 14 万），统一阈值武断，逐房阈值又要多一个参数与一个面板控件。水位存在编排自己的键里（照 `notifiedRooms`），房间库的三个键与 ADR-0003 的单写者边界都不动。

## Considered Options

- **挂在 60 秒的开播状态轮询里**（`refreshRooms` 合并完接着查看点）：少一个 alarm、少一套创建/清除收敛，而且在线状态是刚写回的；代价是请求量 5 倍，且取数节奏被用户的「轮询间隔」设置间接绑架。
- **复用 10 分钟观众数采样 alarm**：不新增 alarm；但那个 alarm 的存在由平台观众数开关决定，会出现「关掉贵宾数采集、看点也不看了」这种莫名其妙的联动。
- **不持久化水位，按「本轮没见过就算新」**：零状态；但 SW 每次冷启动、扩展每次重装都会把整场看点当新的重报一遍，而这正是这个功能最容易变成骚扰的失败形态。
- **热度门槛 / 逐房冷却**：更抗噪；但本轮实测的发布节奏不需要，两者都要新增设置项与面板控件。真被吵到再加冷却（语义照 `watch` 的冷却）。
- **相对本房热度中位数才算「值得通知」**：判据最像「值得看」，照 `danmaku-surge` 的基线思路也做得出；但会给「看点」偷偷加上「只有热门才算看点」的语义，与「有新的就告诉我」不符，还要维护每房的热度分布。
- **水位交给房间库当第四个键**：修剪随房间删除天然发生；但这条状态是**通知纪律**而不是房间事实——`notifiedRooms` 已经把这类状态判给了编排，收进房间库要扩写 CONTEXT.md 与 ADR-0003 的边界，换不来真实收益。

## Consequences

- README 的功能表与支持平台表、设置页的第五张卡片都要出现这个功能；`CONTEXT.md` 增补「看点 / 看点通知 / 看点水位」三条术语。
- 房间被移除或重新添加时编排要清掉该房水位（与 `notifiedRooms` 的处理挨在同一处），否则重新添加的房间会在第一轮就把该场已有的看点报出来。
- 首次观测只记水位的口径让「开关重开」与「换场」自动收敛：隔了一周再打开开关，水位已落后很多，一轮里会有大量「新」看点，但只报最新那一条，不会补报一屏通知。
- 看点的可用性完全取决于平台的 AI 功能（实测有开播房间长期 0 条），设置页面板要让用户预期「开了开关也可能长时间没有通知」。
- 接口是未公开的 `wgapi` 路径，与 ADR 系列记录的所有平台接口一样，平台调整即失效，需要跟随调整。
- `HIGHLIGHT_PLATFORMS`（平台门）留在规则 module，但本 module 内部没有函数读它——读它的是编排取数入口的三层门控与设置页的房间面板（本功能的判定拆在两处：水位判定在规则 module，取数目标筛选在编排）。这与 ADR-0005 里 `WATCH_PLATFORMS` 那张先例不同，那里常量被同文件的 `selectWatchPlan` 读；此处让常量跟着判定走的理由仍是 ADR-0005 的第一条（能在单测里单独 require 驱动），而搬进共享词汇 module 会让它多出一条只有本功能读的事实。判据若从严按「本文件有没有函数读它」执行，这个常量该搬走——真要搬，得连 `CONTEXT.md` 的「房间标识」一起改。
