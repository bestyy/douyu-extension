# 房间状态由房间库单点写入，页面变更经 SW 消息、读取走只读快照

`rooms` / `streamers` 的形状与全部变更原本散在六个写入者手里，每个写入者都「读整个数组 → 改 → 写回」，跨 await 的交错会丢更新：SW 内 `refreshRooms`（读 444 / 写 495）与 `updateVipCount`（读 99 / 写 106）之间，以及设置页拖拽重排（读 354 / 写 384）与每轮轮询写回 `streamers` 之间。因此把这两个数组连同 `settings` 的形状收进房间库（`lib/room-store.js`），由它做唯一写入者：变更操作只接受意图、在模块内部重新读改写，原子性由模块内的串行队列保证；页面的变更请求经 SW 消息到达它，读取走它的只读快照。

## Considered Options

- 单写者 + 意图式变更（选用）：跨上下文交错从根上消除；代价是设置页保存多一次消息往返，且轮询合并、离线清空、平台门控等规则必须由房间库承载。
- 三处上下文各自实例化、各自加锁（否决）：跨上下文仍是 last-writer-wins，只把窗口变窄。
- 只统一 SW 内部、页面继续直写（否决）：最省事，但设置页继续拥有 `streamers` 的形状知识，拖拽重排仍会整批覆盖轮询结果。

## Consequences

- 页面不再出现 `chrome.storage.local` 的写与 `rooms` / `streamers` 形状拼装；新增存储键必须先声明归属（房间库 / 编排 / 盯守 / 桥接通道）。
- 轮询合并、采样值到达、连续两轮离线清空、开关关闭清字段各只实现一次；桥接通道的 `_stripRankCounts` 与 `background.js` 的 `pruneStaleViewerCounts` 合并为同一个操作。
- 观众数提醒仍在「值到达处」判定（见 ADR-0002）：房间库只报告前后值与房间快照，通知由编排发出。
- 任何把页面直写加回来的改动，都会重新引入「按整批列表覆盖」的丢更新窗口——这是本决策最容易被当成冗余而绕开的地方。
