# 观众数提醒复用 10 分钟采样短连并按上升边沿触发，不为实时性新增长连接

「贵宾数超过一定数量就提醒」的语义是「这房热起来了」，不是秒级告警，因此提醒判定直接挂在每 10 分钟一次的观众数采样结果上（斗鱼 `oni` 的贵宾数、B站 `ONLINE_RANK_COUNT` 的高能榜在线数），零新增连接。触发条件是**上升边沿**：数值从阈值以下升到阈值以上时报一次，回落到阈值以下自动重新武装，再次越过再报——持续高位的房间每 10 分钟刷一条通知是打扰，不是提醒。

判定点放在值到达处（`updateVipCount` / `updateRankCount`），而非轮询收敛点：值入口就是「采样结果」这一事实的唯一出口，避免轮询路径与采样路径两处判定口径不一致。

同一次决策还包含**下播清空存量**：连续两轮轮询确认离线后清空该房 `vipCount` / `rankCount`。没有这一步，B站房间的第二场永远不再提醒——未开播收不到 `ONLINE_RANK_COUNT`，旧值一直 ≥ 阈值，永远不存在上升边沿（斗鱼有未开播上报 0 的兜底，B站没有，两个平台行为不对称）。顺带修掉「重新开播瞬间 popup 显示上一场高能榜旧值」的显示瑕疵。用两轮而非一轮，是防单次 API 抖动把在播房间误判为离线、清空后同场重复提醒。

## Considered Options

- 复用采样短连（选用）：零新增连接，天然落实「没开观众数采样就没提醒」的联动；代价是短时高峰可能落在采样间隙里看不到。
- 挂到斗鱼检测长连接的 `oni` 推送（约 6 秒一次）：更实时，但只有开弹幕检测且未超并发上限（5 个）的房间才有这条连接，能力随检测配置与排队状态漂移，用户无法预期。
- 为配了阈值的房间新增长连接：最实时，但与 ADR-0001「只在检测时保持长连接」的取向冲突，且新增限流风险。

## Consequences

- 提醒的实时性上限是采样周期（10 分钟），设置页面板文案已向用户说明「短时高峰可能采不到」。
- `streamers[].vipCount` / `rankCount` 不再只是展示字段：它同时是判定用的「上一次数值」，因此**必须持久化在 storage 里**（原本就是），且不能被轮询覆盖（轮询已有透传逻辑）。
- 无历史值视为 0：新加入的房间、清空后的房间首次采到 ≥ 阈值即提醒；反之，已经存有高值的房间在用户新配阈值时不会补报（没有上升边沿）。
- 联动门控是显式的：总开关 `settings.viewerAlertEnabled` 与该平台观众数开关都要通过才判定，关闭时配置保留、重开即恢复（与弹幕检测总开关的处理一致）。
